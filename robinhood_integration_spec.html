Nothing else in this spec matters until this is reconciled — see §2.

5 · Workstream C — clean per-day / per-week evaluation

What exists for actual trades: per-day daily.py /daily/summary,/daily/history and per-month trades.py:96-129 /trades/monthly-stats — but no per-week rollup, and the rich by-pattern/by-hour/by-symbol breakdown lives on a different table (real_trades) real_trades.py:232-348. Build:

  1. Weekly (and daily/monthly) trade report over matched_trades + daily_trades: P&L, win rate, avg win/loss, expectancy, R-multiple, gross vs net (fees), by-symbol, stock vs options, best/worst trade, win/loss streaks. Reuse _week_bounds performance.py:342-357 and port the breakdown logic from real-trades/performance-breakdown onto the imported-fills table.
  2. One report surface in the web app (extend the Daily Target page or a new "Trades" tab) with a day / week / month / all toggle and the equity curve — instead of today's single all-time running total DailyTargetPage.tsx:788,981.
  3. The high-value one you didn't ask for — alert→fill attribution. Join your Robinhood fills to the scanner alerts (alerts table) by symbol+date: did you take the signal, and how did the trade play vs the alert's entry/stop/target? That turns this from a P&L viewer into a measurement of the platform's real edge — which alerts you act on, and whether acting on them makes money. This is the single most useful thing the broker data unlocks.

6 · Workstream D — correctness bug to fold in

Options realized P&L is 100× too low in matched_trades. The FIFO matcher computes P&L from per-share prices with no contract multiplier trade_matcher.py:52-53,74, and insert_matched_trades stores it raw db.py:1750-1763. The ×100 multiplier exists only in the Daily Target bridge daily_target_sync.py:35,99-100, so daily_trades.pnl is right but matched_trades.realized_pnl is not — which corrupts /trades/history, /trades/equity-curve, /trades/monthly-stats trades.py:82,335,112 and SyncResult.realized_pnl. Fix at the matched_trades boundary (in trade_matcher or at insert), and reconcile with the bridge's multiplier so it isn't double-applied. New Robinhood imports and old statement history are both affected — fixing it rewrites historical numbers, so it's a deliberate, announced change.

7 · Other thoughts (my additions)

  • Fees & slippage in P&L. Once fees are captured (§3 P1), report net P&L and surface slippage vs the alert's intended entry — the difference between "the signal worked" and "I filled well."
  • Contributions vs performance. Without transfers (get_bank_transfers), an equity curve conflates deposits with gains. Pull them before you show % returns.
  • Reconciliation. Add a check that our computed account P&L for a period is within a tolerance of Robinhood's own reported number — catches multiplier/fee/dedup drift early.
  • Session-expiry ops. The robin_stocks session pickle expires in weeks (or on a password/security event). The job already Telegrams on login failure main.py:556-557; add a "session age / last-success" indicator to the UI so a silent stall is visible, and document the re-seed (local login → base64 → ROBINHOOD_SESSION_B64).
  • Security. ROBINHOOD_SESSION_B64 and ROBINHOOD_PASSWORD are live credentials — Railway secrets only, never logged, never in the repo. The Postgres DSN has been exposed in chat during this work — rotate it.
  • Scale = SnapTrade, not robin_stocks. The unofficial API + per-user password/pickle model does not scale to customers (ToS, credential custody, fragility). PR #544 (SnapTrade, currently open) is the compliant multi-account path; treat robin_stocks as the founder-only bootstrap and SnapTrade as the productization step. Workstream C's reporting should read from a broker-agnostic matched_trades/daily_trades so it survives the swap.
  • Out of scope (flag, don't build): tax lots / wash-sale accounting — leave to Robinhood's 1099, which the statement importer already parses.

8 · Trade execution — deferred (read-only options first)

robin_stocks can place live orders (order_buy_market, order_sell_limit, order_buy_option_limit, crypto, stop/limit, tif gtc/gfd/ioc/opg). The codebase places zero live orders today — everything is signals + paper (paper_trades, alerting/paper_trader.py). grep: no order_* call anywhere

Live execution is explicitly OUT of scope for now. It's real, irreversible money through an unofficial ToS-violating API, with broker-dealer/adviser regulatory exposure the moment it touches anyone but the founder. If ever pursued: your own account only, confirm-before-place (never fire-and-forget on a signal), hard risk limits + kill-switch, dry-run default, full audit + reconciliation, paper-proven first, and a compliance review. Customer execution goes through SnapTrade + legal, not robin_stocks.
Chosen first step (decided 2026-09-09): read-only options analytics only. Pull the options chain + greeks (delta/theta/gamma/vega/IV) via rh.find_options_by_expiration(symbols, expirationDate, optionType) and get_option_market_data_by_id — pure analysis, no execution risk. Feeds option-trade-quality evaluation (§5) and setup screening. This is where we start slow.

now
Delivery is GLOBAL — monitor.py:977-984: "if a redesign rule fires, it is delivered… the per-user type toggles are NOT consulted." Every rule in ENABLED_RULES that fires pushes. There is no per-rule off switch in effect.

See every enabled rule in Settings and toggle off the noisy ones — those still record to the feed but stop pushing (Telegram + in-app).

Change: re-wire the delivery gate to honor a per-rule toggle. The plumbing exists and is just bypassed:

Wiring:

a. Delivery gate. At the gate (monitor.py:988, right after _at_val = signal.alert_type.value), consult the SCAN user's UserAlertTypePref: deliver unless the rule is toggled OFF — opt-out, default ON, so nothing changes until you flip something. On OFF, set _send_notification = False and record _suppressed = "rule_toggled_off" — the Alert row is still written, so the feed shows it (and why it didn't push), matching the existing suppression pattern (monitor.py:985-992).
b. Catalog audit. Register every enabled scanner rule in ALERT_TYPE_CATALOG so it shows in Settings. Audit the newest rules specifically — the reclaim ladder, pwh/pmh_breakout_retest, rsi_30_35, the 2h swing_reclaim_*, and the new W/M/Q holds (pwh/pwl/pmh/pml/pqh/pql_reclaim + their swing_reclaim_* twins). Any missing from the catalog can't be toggled.
c. UI. Settings → Alert Types already lists catalogued types with switches (driven by /alert-config). No new screen — the audit in (b) makes the new rules appear there.
Why opt-out, not opt-in: the GLOBAL gate was deliberately introduced (monitor.py:980-984) because opt-in prefs silently muted the new reclaims for anyone who'd toggled the deprecated bounce types — "Phase 1 shipped to an empty phone." Opt-out (default ON) keeps that safety: everything delivers until you explicitly silence a specific noisy rule.

3 · Scope & risk

  • Single-user — both controls read vbolofinde's rows only. No per-user branching.
  • Protected files touched: monitor.py (universe read + delivery gate). Change is additive and guarded (empty-watchlist fallback; default-ON toggle) so existing behaviour is unchanged until you edit the watchlist or flip a rule. Impact analysis + tests before the edit, per project rules.
  • No redeploy for content changes — once wired, editing the watchlist or a toggle takes effect on the next 3-min poll. (A code change to the wiring itself still needs the Railway worker restart.)
  • Delivery-only toggle — a toggled-off rule still fires and records to the feed; it just doesn't push. Nothing is lost.
